# 第 7～8 周笔记：补欠账 + 内核 MCP + 需求雷达（种子 2）

## 一句话本质
**同一个"带来源核对的调研 Agent"，写一次，通过 MCP 给两个应用用**；而"不编造"这件事，靠的是一轮轮用真实数据量化、再把漏网的模式变成程序规则——提示词只能降低，程序规则才能兜底。

## 一、求职 Agent 补的欠账

| 项 | 做法 | 验证 |
|---|---|---|
| 👍👎 反馈 | 筛选建议、每条改写、每道面试题都能点；**只记"哪类第几条、赞还是踩"，不存任何文字**（文字里有简历内容） | `/api/stats` 出汇总：赞踩数、改写保留率 |
| 改写后的简历导出 Word | 按改写记录的行号（容错 ±1 行）在原文里精确查找替换，改过的段落标黄；找不到的不猜，列在文末 | 真实流程：6 条改写全部定位成功（5 条跨 PDF 断行），0 条要手动改 |
| 评测集补 2 份模拟简历 | 前端转 AI（3 年）、Python 后端 + RAG（5 年），全部虚构 | 见下面"编造率" |
| 服务端日志 | 流式任务出错原来只发给前端，线上无从查起；现在同时写日志 | — |

## 二、编造率：从 18% 到 0 的过程

做法：3 份简历 × 3 个 JD 跑"差距分析 → 改写 → 两层校验"，**我逐条人工判断所有自动通过的改写**（被拦下的会交给用户确认，不算漏网）。

| 轮 | 改了什么 | 漏网（编造/夸大且自动通过） | 需人工确认的比例 |
|---|---|---|---|
| 1 | 原样 | 9 / 50 = **18%** | 52% |
| 2 | 复核提示词逐短语核对；改写提示词禁止追加描述、禁止弱化 | 4 / 43 = 9% | 65% |
| 3 | 程序检查加"新增表述"（改写里连续 ≥4 个中文字在原文找不到依据）+ 中文技术词表 | 2 / 32 = 6% | 81% |
| 4 | 程序检查加"去掉岗位限定词"（前端开发→AI 应用开发）；**全新一轮** | **0 / 41** | 83% |

| 发现 | 教训 |
|---|---|
| 24 条人工构造的样本（整句篡改）上漏检 0，真实改写里却漏 18% | **合成样本测不出真实问题**：真实的编造是"一句真话后面悄悄加一小段"，模型复核对此不敏感 |
| 把真实漏网写法做成合成样本，旧提示词也能 5/5 拦住 | 复核时原文是几行上下文，上下文一多模型就放松——只有真实评测能发现 |
| 提示词里明确点名"原理"，模型复核还是放过"……的原理与工程落地" | 提示词只能降低概率，确定性的事交给程序 |
| "新增表述"检测用逐字顺序比对，28 条正常改写误报 20 条 | 改写常调整语序；改成"二字词在原文任意位置出现即有依据"（与顺序无关），误报降到 11 条 |
| 改写会把"精通"写成"掌握" | 不是编造但对用户不利，改写提示词加"不得弱化" |

代价：需要人工确认的改写从一半升到 83%。宁可多问也不放编造进简历，这是产品的核心承诺；**下一步要让改写本身更保守**（少改、只改真正提升匹配度的）。
局限：规则是看着前 3 轮设计的，第 4 轮虽是全新运行，但还是同样的简历和 JD，要换新数据再验证。

## 三、内核 MCP Server

| 概念 | 是什么 |
|---|---|
| MCP | AI 应用调用外部工具的标准协议。工具写一次，Dify、Claude Desktop、Cursor 等都能发现并调用 |
| Streamable HTTP | MCP 的网络传输方式：一个 HTTP 地址（`/mcp`），客户端 POST JSON-RPC 请求 |
| DNS 重绑定防护 | 只接受白名单里的 Host 头，防止恶意网页借浏览器访问本机服务 |

| 文件 | 作用 |
|---|---|
| `src/job_agent/mcp_server.py` | 两个工具：`research_company`（求职视角）、`research_competitors`（独立开发者视角）；Bearer Token 鉴权 |
| `src/job_agent/radar/competitor.py` | 竞品调研：产品功能、定价、用户抱怨、没解决好的地方 |
| `job/research.py` 的 `run_research` | 抽出来的通用骨架：搜索次数封顶 → 结构化输出 → 来源链接必须是本次搜索返回过的 |

踩坑：mcp SDK 已到 2.x，`FastMCP` 改名 `MCPServer`；会话管理器一个进程只能启动一次（测试里不能开两个客户端）；Dify 工作流里引用 MCP 工具用"服务器标识"（`job-kernel`），所以 DSL 可以提前生成。

## 四、需求雷达（种子 2，Dify）

详见 `../demand-radar/README.md`。流程：领域 → 抓 HN / GitHub / V2EX → 逐帖判需求（原话核对）→ 痛点聚类打分（程序计数）→ 头号痛点经 MCP 调内核做竞品调研 → 报告。

| 评测 | 结果 |
|---|---|
| 端到端（本机 Dify 1.18） | 记账、笔记软件、简历工具都跑通（含经 MCP 的竞品调研）；按来源并行判断后从 279 秒降到 140～170 秒 |
| 需求判定：快模型 vs 强模型（4 个领域 360 条帖子） | 一致 70%；不一致的 108 条里 82 条来自 GitHub。抽查 30 条：**快模型对 25 条**，强模型对 2 条，3 条两可——强模型把"任何功能请求"都算需求，忽略了"和领域相关" |
| GitHub 来源 | 按点赞排序会搜出全站热门的无关 issue（"记账"搜出 Go 语言提案）；改成只按标题匹配后切题，但大众话题下多是学生项目的开发任务——**GitHub 只适合开发者工具类话题** |
| 竞品调研两种做法（4 个领域） | A 模型节点直接问：131 个链接，具体页面 85 个里 **13 个 404**（如 `apps.apple.com/cn/app/id1234567890`）；B 内核调研 Agent：41 个链接，**0 个 404**、全部来自搜索结果。代价：B 贵约 15 倍（24.7 分 vs 1.7 分/次） |
| 原话核对 | 3 次运行共判定需求 86 条，因原话对不上被丢弃 0 条 |

| 实测踩坑 | 处理 |
|---|---|
| MCP 工具调用成功，报告里竞品一节却是空的 | Dify 把 MCP 工具的结构化返回放在工具节点的 `json` 输出里，`text` 是空的；报告节点改成两个都读 |
| 改了内核代码，Dify 调到的还是旧逻辑 | MCP Server 是独立进程，**改完要重启** |

已知局限：同一领域跑两次，头号痛点可能不同（"简历工具"一次是"付费墙"，一次是"重复撰写低效"）——聚类有波动；以后可以把多次运行的痛点合并、按出现次数排序。

人工标注：`../demand-radar/eval/out/labels.csv` 有 360 条（快模型、强模型的判断都在），`human` 列留给人工填。

## 五、意外发现：搜索服务"成功但为空"

2026-10-29 智谱 `search_std`、`search_pro` 对任何查询都返回 HTTP 200 + 空结果，搜狗、夸克两档正常。
调研 Agent 表现正确（如实写"没搜到"，没有编造），但**整个功能静默失效、不报任何错**。
修：引擎按顺序试，空结果就换下一个，并写日志。**线上 job.wyphub.com 需要重新部署才生效。**
