# 第 4 周笔记：多模型对比 + 上线准备

## 一句话本质
**模型选型靠数据，上线靠"最坏情况有兜底"**：同一批任务换 6 个模型跑，按质量 / 成本 / 耗时定每一步用谁；上线前把"最坏会怎样"逐条想一遍（被刷额度、塞超长文本、硬盘写满、伪造 IP），每条都有程序兜底。

## 多模型对比

数据来自 `evals/run_model_compare.py`，原始表在 `evals/out/model_compare.md`。成本单位：人民币分 / 每个 JD。

| 模型 | 筛选质量 | 筛选耗时 / 成本 | 防编造复核 漏检·误报 | 结论 |
|---|---|---|---|---|
| deepseek-flash | 召回 100%，风险 90%/100%，引用问题 0 | 10s / 2.9 分 | 0 · 0 | **筛选用它**：质量、速度、成本最均衡 |
| deepseek-v4-pro | 风险 100%/100%（参照模型） | 20s / 10.3 分 | 0 · 0 | **深度准备用它**：低频高价值，防编造是卖点 |
| qwen-plus | 风险 78%/78%，引用问题 1.6/JD | 72s / 1.1 分 | 0 · 1 | 最便宜但慢且差，不用 |
| qwen3.7-plus | 风险 100%/100%，引用问题 1.9/JD | 36s / 2.9 分 | 0 · 0 | **DeepSeek 出错时的备用** |
| Claude Haiku 5.5 | 风险 100%/89% | 35s / 3.5 分 | 0 · 3 | 误报偏多 |
| Claude Sonnet 5.5 | 召回 100%，分差最小（4） | 28s / 42.6 分 | 0 · 0 | 质量好，但贵 15 倍 |

模型路由（`core/llm.py`）：筛选 = flash，深度准备 = v4-pro，任一出错自动切 qwen3.7-plus（`with_fallbacks`；只给服务器自己的 Key 兜底，用户自带 Key 时不切，免得花服务器的通义额度）。
实测：DeepSeek Key 设成无效值，解析自动由 qwen3.7-plus 完成（13 秒）。

| 对比中踩的坑 | 处理 |
|---|---|
| Sonnet 5.5（经 OpenRouter）结构化输出全部 400 | 原始报错：不支持强制指定工具（`tool_choice` 为 tool/any）。OpenRouter 上的 Claude 改用 `json_schema` 方式 |
| Haiku 换成 json_schema 后，耗时 13s→35s、误报 2→3 | 同一模型换输出方式，结果也会变；**对比时要固定调用方式** |
| flash 复核误报上周 2 条、这周 0 条 | 同一评测多次运行有波动，只看大趋势，不抠个位数 |

| 任务 | 怎么评 |
|---|---|
| 筛选链路（7 个有标注的 JD） | 解析：硬性要求召回、关键词 F1；差距分析：引用核对问题数、与 v4-pro 的分差；风险：类型准确率 / 召回率 |
| 防编造复核（24 条人工样本） | 模型单独漏检、误报；加上程序检查后的合计漏检 |
| 成本 | tokens × 官网单价（DeepSeek 按高峰价；美元按 7.1 换算） |

## 上线前补的"最坏情况"

| 最坏情况 | 不补会怎样 | 做法 |
|---|---|---|
| 经 Tunnel 转发后所有请求来源都是 127.0.0.1 | 全体用户共用一份免费额度，第一个人用完大家都不能用 | 从 `CF-Connecting-IP` 取真实 IP，且只信来自本机的请求（直连可以伪造请求头） |
| 有人换 IP 刷免费额度 | 费用无上限 | 全站每天总上限 200 个 JD（约 6 元封顶） |
| 塞几十万字的简历 / JD | 一次请求烧掉很多 token | 简历 2 万字、JD 1 万字、文件 5MB 上限 |
| 带一个假的 DeepSeek Key 绕过额度去用截图识别 | 截图识别用的是服务器的通义 Key，白嫖 | 截图识别不管带不带 Key 都计入额度 |
| 深度准备存档只增不删 | 硬盘慢慢写满 | 每小时检查一次，删 7 天前的任务 |
| 服务吃满内存 | 拖垮同机的 OCR 演示和 VPN | systemd `MemoryMax=1200M`，超限只杀本服务 |

## 部署方式（沿用 OCR 演示的做法）

| 选择 | 原因 |
|---|---|
| 复用已有 Cloudflare Tunnel，只加一条路由 | 不开新端口；HTTPS 由 Cloudflare 负责 |
| systemd + uv、专用用户、只听 127.0.0.1 | 隔离；服务出问题碰不到其他服务 |
| 所有新装的东西记清单，下线脚本只删清单里的 | 能干净下线，不误删同机的其他服务 |
| 本机打包直传，不推 GitHub | 代码暂不公开；包里不含简历、评测数据 |
| 改 Tunnel 配置前先在本地演练 sed | 加路由、删路由后能逐字还原原配置，才敢动线上 |

## 上线状态（2026-10-28 已上线：https://job.wyphub.com）

| 验证 | 结果 |
|---|---|
| 公网健康检查、首页 | 200；OCR 演示同时正常 |
| 线上筛选（2 个 JD，真实模型） | 13 秒，8 条进度推送，结果与本地评测一致 |
| 线上深度准备 | 37 秒停在人工确认（6 条）→ 全部拒绝后恢复 → 53 秒出报告；无占位符残留，9 道面试题 |
| 线上隐私 | 存档（含 SQLite 的 WAL 文件）里姓名、手机号、邮箱出现 0 次 |
| 资源 | 服务常驻约 105MB 内存 |
| 重复部署 | 第二次执行 `push.ps1` 只更新代码，不重复改 Tunnel |

| 上线后才发现的 | 处理 |
|---|---|
| 存档主文件里一个占位符都没有，差点误判"没写进去" | SQLite 开了 WAL：新数据先写进 `-wal` 文件，检查要连它一起查 |
| 存档文件权限 644，同机其他用户可读 | 服务加 `UMask=0077`，应用目录 700 |
| 本机 Python 往 ssh 管道输出中文乱码 | Windows 默认 GBK，加 `PYTHONIOENCODING=utf-8` |
